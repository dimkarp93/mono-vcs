# mono-vcs

`mono-vcs` — CLI для массовой синхронизации локальных git-клонов с инстансом
GitLab. Это самодостаточный **один статический бинарь**: клиентам не нужен
никакой рантайм, нужен только `git` в `PATH`.

Конфиг хранится в формате **JSON** (см. ниже).

## Сборка

Нужен тулчейн Go (проект таргетит Go 1.26.1). Если Go установлен в локальный
префикс:

```bash
export PATH="$HOME/.local/go/bin:$PATH"
```

Затем:

```bash
make build                 # -> ./mono-vcs (статический бинарь)
make run ARGS='--help'     # собрать и запустить
make test                  # весь набор тестов
make check                 # vet + test
```

`make` без аргументов печатает список целей и примеры запуска.

### Кросс-компиляция для клиентов

```bash
make dist     # -> dist/mono-vcs-{linux,darwin}-{amd64,arm64}.tar.gz + dist/SHA256SUMS
```

Сборка идёт с `CGO_ENABLED=0 -trimpath -ldflags="-s -w -X main.version=<ver>"` →
полностью статический бинарь без зависимости от libc, с вшитой версией из
`versions.txt`. Формат архивов и `SHA256SUMS` совместим с установщиком
`github_install.sh` (см. ниже).

## Установка у клиента

Дистрибуция — **только бинарь**. Никаких дополнительных файлов не требуется:
конфиг создаётся в рантайме командой `mono-vcs init`, а `git` у клиента уже есть.

Рекомендуемый способ — универсальный установщик (репозиторий — `<owner>/mono-vcs`,
имя бинаря совпадает с именем репозитория — `mono-vcs`):

```bash
github_install.sh <owner>/mono-vcs            # имя бинаря mono-vcs определится из ассета
github_install.sh -u <owner>/mono-vcs         # обновить, только если есть новее
```

Установщик скачивает `mono-vcs-<os>-<arch>.tar.gz`, проверяет `SHA256SUMS` и
кладёт бинарь в выбранный каталог. Локально из готового архива:
`github_install.sh -F dist/mono-vcs-linux-amd64.tar.gz`.

Сборка из исходников: `make install` (ставит в `/usr/local/bin/mono-vcs`).

## Релиз

Версия живёт в `versions.txt` (голый semver). Чтобы выпустить релиз: подбампить
версию и смержить в `main`/`master` — CI (`.github/workflows/release.yml`) сам
соберёт архивы для 4 платформ, сгенерирует `SHA256SUMS` и создаст GitHub Release
с тегом `vX.Y.Z` (идемпотентно: если тег уже есть — пропускает).

```bash
make bump-patch   # 0.1.0 -> 0.1.1   (есть и bump-minor / bump-major)
git commit -am "release X.Y.Z" && git push   # мерж в main запускает релиз
```

## Конфиг (`~/.config/mono-vcs`)

Управляется через `mono-vcs init`. Путь учитывает `$XDG_CONFIG_HOME`. Токен
**не** хранится. Формат — JSON:

```json
{
  "gl-url": "https://gitlab.company.com",
  "jobs": 4,
  "db-path": "/home/user/.local/mono-vcs/state.json",
  "aliases-path": "/home/user/.local/mono-vcs/aliases.json"
}
```

`aliases-path` — файл с пользовательскими алиасами (`mono-vcs alias`). По
умолчанию `~/.local/mono-vcs/aliases.json`; как и `db-path`, ключ нужен, только
чтобы положить файл в другое место.

`db-path` — файл состояния, в котором mono-vcs хранит дефолтную ветку каждого
локального репозитория. По умолчанию `~/.local/mono-vcs/state.json`; ключ в
конфиге нужен, чтобы положить его в другое место (общий воркспейс, отдельный
профиль). Файл создаётся при первой записи, ключи в нём — абсолютные пути репо.

Ключа `main-branch` больше нет (как и флага `--main-branch`): дефолтная ветка
берётся из GitLab и хранится в `db-path`, а не угадывается. Старые конфиги с этим
ключом читаются без ошибки — лишнее поле просто игнорируется.

## Раскладка локальных папок

`mono-vcs clone` кладёт репозиторий в путь, **точно равный** `path_with_namespace`
из GitLab, относительно текущей директории. Никаких преобразований пути нет:

```
mono/backend/api    ->  ./mono/backend/api
mono/libs/util      ->  ./mono/libs/util
other/tools/deploy  ->  ./other/tools/deploy
```

Раскладка не зависит от того, какие проекты видит токен, поэтому одинакова на
любой машине и не меняется при выдаче или отзыве доступа.

> **Изменение поведения (0.4.0).** Раньше, если *все* видимые проекты лежали в
> одной верхней группе, эта группа молча срезалась из локального пути
> (`mono/backend/api` → `./backend/api`). Префикс пересчитывался на каждом
> запуске, поэтому появление одного проекта из другой группы меняло раскладку
> всего воркспейса. См. «Миграция со старой раскладки».

## Миграция со старой раскладки

Актуально, только если воркспейс был склонирован версией до 0.4.0 **и** все
проекты лежали в одной верхней группе — то есть локально нет папки с именем
группы. Мигрировать нужно только сами директории: `mono-vcs` не хранит никакого
состояния о том, где лежат репозитории.

Обычные клоны переживают перемещение без последствий — внутри `.git` нет
абсолютных путей, так что незакоммиченные изменения, стэши и локальные
фиче-ветки остаются на месте:

```bash
cd ~/work/mono-workspace
mkdir -p mono
for d in */; do
  [ "$d" = "mono/" ] && continue
  mv "$d" mono/
done

mono-vcs clone      # ожидаем "nothing to clone" — раскладка совпала
mono-vcs list --all
```

Клонировать заново в чистую папку вместо `mv` не стоит: потеряются
незакоммиченные изменения, стэши и локальные фиче-ветки — ровно то, ради чего
существуют `new`/`switch`/`stash`/`features`, — плюс это повторный трафик на весь
набор репозиториев. Это оправдано, только если воркспейс заведомо чистый
(`mono-vcs list --dirty --features` ничего не показывает).

## Дефолтная ветка

Единственный источник истины — `default_branch` проекта в GitLab. Никаких
догадок по именам веток (списка кандидатов `main`/`master`/`develop` и фолбэка из
конфига нет) и никакого чтения `origin/HEAD`: этот ref — снимок момента
`git clone`, обычный `git fetch` его не обновляет, и после переименования ветки на
сервере он указывает на ветку, которой уже нет.

Ответ GitLab кэшируется в файле состояния (`db-path`, по умолчанию
`~/.local/mono-vcs/state.json`), и дальше порядок такой:

1. **Файл состояния.** Если запись по репозиторию есть — берётся она, без сети.
2. **GitLab.** Если записи нет, команда идёт в API (нужны `gl-url` и токен),
   сопоставляет репозиторий по `path_with_namespace` и сразу сохраняет ответ в
   файл состояния.

`list` и `pull` ходят в API всегда и обновляют записи всех локальных репо, так что
после любого из них остальные команды (`update`, `switch`, `new`, `finish`,
`features`, `default-branch`) работают офлайн. Исключение — `done`: она всегда
делает `git fetch --prune` в каждом репозитории, иначе судить о влитости нельзя. Токен для них спрашивается лениво —
только если в файле состояния чего-то не хватает. У `pull` обращение к API
best-effort: если GitLab недоступен, он предупредит и продолжит по файлу состояния.

Если записи нет и GitLab не отдал проект (нет доступа, репо переехало, склонировано
не из этого GitLab, сеть недоступна) — репозиторий **пропускается с ошибкой**, а
команда завершается ненулевым кодом:

```
$ mono-vcs update
[1/2] updated    mono/backend/api
[2/2] ERROR      mono/tools/x: the default branch is unknown — no entry in the
                 state db and GitLab reports no project — run `mono-vcs list` to refresh
1 repo(s) skipped — the default branch could not be determined
```

Чинится `mono-vcs list` или `mono-vcs pull` — они перезапишут запись из GitLab.

Исключение — `mono-vcs switch <branch>` с явным именем ветки: он переключается на
неё, не спрашивая про дефолтную. Знание дефолта нужно ему только для `switch` без
аргумента и для фолбэк-подтягивания, когда искомой ветки в репозитории нет.

Посмотреть текущее состояние — `mono-vcs default-branch`; нерешённые репозитории
он помечает `(unresolved)`.

## `mr` — публикация фичи

`mono-vcs mr [branch]` пушит фиче-ветку во **все** репозитории, где она есть, с
push-опциями GitLab, то есть одним махом открывает по merge request'у на каждый
репозиторий фичи:

```
git -C <repo> push -u origin refs/heads/<branch>:refs/heads/<branch> \
    -o merge_request.create \
    -o merge_request.remove_source_branch
```

Заголовок MR всегда начинается с тикета: `-o merge_request.title=[<ticket>] <text>`,
где `<ticket>` — начало имени ветки до второго дефиса: подходят и `MVPAY-290`,
и `MVPAY-290-oplata` — оба дают `MVPAY-290`. Второй сегмент должен быть числом.
Без `-title` передаётся просто `[<ticket>]`; если `-title` уже начинается с `[`,
префикс не дублируется. Ветка, из имени которой тикет не вычленяется
(`hotfix`, `practice-improves`), отвергается — MR не создаётся.

Фича определяется однозначно, иначе команда ничего не делает:

- **явно** — позиционным аргументом (`mono-vcs mr MVPAY-290`). Проверяется, что
  такая ветка существует хотя бы в одном репозитории и что **все** репозитории,
  где она есть, сейчас на ней переключены;
- **из контекста** — без аргумента. Среди репозиториев, стоящих не на своей
  дефолтной ветке, должно быть ровно одно имя ветки, и все репозитории, где эта
  ветка есть локально, должны быть на неё переключены.

Если условие нарушено (ветки нет, активных фич несколько, часть репозиториев
осталась на дефолтной ветке), команда завершается с ошибкой и подсказкой
`mono-vcs switch <branch>` — так фича всегда публикуется целиком.

Дополнительно: если хотя бы в одном репозитории фичи есть незакоммиченные
изменения, не пушится **ничего** — сначала коммит или `mono-vcs stash`.
Репозитории, где локальная ветка уже совпадает с `origin/<branch>`, пропускаются
(`up-to-date`) — push не вызывается, а значит и новый MR там не создаётся.

`--dry-run` печатает план без единого git-вызова.

## `pull` против `update`

Обе команды подтягивают дефолтную ветку из `origin`, но по-разному относятся к
рабочему дереву.

`pull` — **обновить дефолтные ветки, не трогая воркспейс**. Для каждого репо:

- текущая ветка = дефолтная → `git pull --ff-only`;
- иначе → `git fetch origin refs/heads/<d>:refs/heads/<d> +refs/heads/<d>:refs/remotes/origin/<d>`.

Во втором случае ни `HEAD`, ни рабочее дерево, ни незакоммиченные изменения не
затрагиваются: обновляются только ссылки. Поэтому `pull` безопасно звать посреди
работы на фиче-ветке — а когда потом переключишься на дефолтную (`mono-vcs switch`),
там уже будет свежий код. Первый refspec идёт без `+`, так что локальные коммиты в
дефолтной ветке не затираются: репо помечается `diverged` и пропускается.

`update` — **переложить свою работу на свежую дефолтную ветку**: `checkout`
дефолтной, `pull --ff-only`, возврат на исходную ветку и `rebase` на дефолтную.
Пропускает репо с незакоммиченными изменениями и может остановиться на конфликте
ребейза.

Правило: `pull` — когда нужно просто догнать `origin`; `update` — когда нужно ещё и
перенести фиче-ветки поверх.

## Жизненный цикл фичи: `new` → `mr` → `done` / `finish`

`new <feat>` — **войти в фичу во всех репозиториях**. В каждом репо:

- ветки нет → `git checkout -b <feat> <default-branch>` — база всегда дефолтная
  ветка, а не та, на которой репозиторий стоял сейчас;
- ветка уже есть → просто `git checkout <feat>`; история существующей ветки не
  переписывается, наработанные коммиты остаются на месте;
- незакоммиченные и неотслеживаемые файлы **переезжают на фичу**: перед
  переключением они уходят в `git stash push --include-untracked`, после —
  возвращаются через `git stash pop`. Если `pop` упёрся в конфликт, репозиторий
  помечается `conflict`, а стеш остаётся на месте (`git stash list`).

Ветка создаётся только локально, без `push`; в сеть `new` не ходит.

`finish <feat>` — **выйти из фичи и забыть её**. В каждом репо, где ветка есть:
`git reset --hard HEAD` + `git clean -fd`, затем `checkout` дефолтной,
`pull --ff-only` и `git branch -D <feat>`. Незакоммиченные и неотслеживаемые
файлы отбрасываются без вопросов — в этом и смысл команды: после неё воркспейс
гарантированно чистый и стоит на свежей дефолтной ветке. Игнорируемые файлы
(`.gitignore`) сохраняются.

`done` — **убрать локальные ветки уже влитых фич**. В отличие от остальных
команд, `done` не принимает ни `-repo`, ни `-feat`, ни имя ветки: она всегда
проходит по всем репозиториям и всем их фиче-веткам. Для каждого репозитория:

1. `git fetch --prune --quiet origin`; если fetch упал — репозиторий
   пропускается целиком, по устаревшим ссылкам ветки не удаляются;
2. точка сравнения — `origin/<default-branch>`, а если такого рефа нет —
   локальная `<default-branch>`;
3. ветка удаляется, только если выполнены оба условия:
   - если она сейчас вычекаучена, рабочее дерево чистое (нет незакоммиченных и
     неотслеживаемых файлов) — иначе `dirty` и ветка остаётся;
   - `git merge-base --is-ancestor <branch> <target>` вернул 0, то есть все
     коммиты ветки уже лежат в истории дефолтной.

Критерий намеренно строгий: ложного «влито» он не даёт никогда. Обратная сторона —
rebase- и squash-мерджи переписывают SHA, и такие ветки `done` не распознает
(статус `open`); их убирают вручную через `finish`.

Ветки удаляются без подтверждения — список удаляемого печатается перед удалением. Если
удаляемая ветка вычекаучена, репозиторий сначала переходит на дефолтную и
подтягивает её.

## Примеры запуска

```bash
mono-vcs init                                   # настроить ~/.config/mono-vcs
mono-vcs list --all                             # все репозитории с цветовой разметкой
mono-vcs clone                                  # gl-url берётся из конфига
mono-vcs pull                                   # обновить дефолтные ветки, не трогая воркспейс
mono-vcs pull --dry-run                         # показать план без действий
mono-vcs update                                 # переключиться на дефолтную, подтянуть, ребейзнуть фичи
mono-vcs default-branch                         # какая дефолтная ветка у каждого репо
mono-vcs stash ; mono-vcs unstash
mono-vcs features                               # таблица фиче-веток
mono-vcs new MVPAY-290 -repo apigateway,payments  # перейти на ветку от дефолтной (локально)
mono-vcs switch my-feature                      # переключить все репо
mono-vcs switch                                 # вернуть все репо на их дефолтную ветку
mono-vcs mr                                     # запушить активную фичу и открыть MR везде
mono-vcs mr MVPAY-290-oplata -title "оплата"     # то же с явной веткой; MR получит заголовок [MVPAY-290] оплата
mono-vcs do git status -s                       # выполнить команду в каждом репо
mono-vcs do -feat MVPAY-290 git status -s       # только репо, где есть ветка MVPAY-290
mono-vcs do git commit -m "два слова"           # кавычки сохраняются: это один аргумент
mono-vcs do "git fetch && git status -s"        # один аргумент — это шелл-строка целиком
mono-vcs done                                   # убрать локальные ветки влитых фич
mono-vcs finish MVPAY-290                       # выбросить фичу и вернуться на дефолтную
mono-vcs alias ls                               # какие есть алиасы remote'ов
mono-vcs alias remote work gitlab.mycompany     # завести кастомный алиас
mono-vcs do -remote work git status -s          # только репо с этого хостинга
```

Про кавычки в `do`: если после `do` идёт несколько аргументов, они трактуются как готовый argv —
границы аргументов сохраняются, шелл-метасимволы внутри них не интерпретируются. Если аргумент
ровно один, он передаётся в `sh -c` как есть, так что `&&`, `|`, `;` и подстановки работают.

Те же сценарии через Makefile: `make run ARGS='list --all'` и т.д.

### Выбор репозиториев: `-repo`, `-feat` и `-remote`

Любая команда, принимающая `-repo`, также принимает `-feat | -f <feat-name>`
и `-remote`:

- `-repo` — ограничить по имени/папке/пути (повторяемый, через запятую):
  - `api` — по имени папки репозитория на любом уровне;
  - `backend/` — по группе; совпадает с любым сегментом пути, так что и
    `mono/` и `backend/` найдут `mono/backend/api`;
  - `backend/api` — по пути; совпадает по суффиксу на границе сегмента, так что
    находит и `mono/backend/api`.
- `-feat | -f` — ограничить репозиториями, где **локально существует ветка** с
  таким именем (та же трактовка «фичи», что и у `mono-vcs features`), независимо
  от того, переключён ли на неё репозиторий.

- `-remote` — ограничить репозиториями с подходящим git-remote (повторяемый,
  через запятую). Значением может быть полный URL remote'а
  (`git@github.com:grp/web.git`), хост (`github.com`), системный алиас
  (`github`) или кастомный алиас (см. `mono-vcs alias`). Репозиторий подходит,
  если совпал **любой** из его remote'ов, а не только `origin`.

`-repo` и `-feat` **взаимоисключающи** — передавать оба сразу нельзя (ошибка).
`-remote` — независимое измерение и комбинируется с любым из них по «И»:
`mono-vcs do -repo api -remote github git status -s` возьмёт только те репо, что
попали и в `-repo`, и в `-remote`. Если не указано ничего, команда работает по
всем репозиториям, как и раньше.

`done` и `mr` по-прежнему не принимают никаких фильтров, включая `-remote`: они
намеренно работают по всем репозиториям сразу.

### Remote'ы и алиасы

`list` и `features` показывают, с какого хостинга приехал каждый репозиторий:
отдельной колонкой с коротким алиасом и блоком `remotes:` под выводом, где у
каждого алиаса видны хост и пример URL.

**Системный алиас** выводится из домена: от хоста отбрасывается последний
сегмент — `github.com` → `github`, `gitlab.com` → `gitlab`,
`gitlab.mycompany.com` → `gitlab.mycompany`. Если два хоста воркспейса дали
одинаковый алиас (`gitlab.com` и `gitlab.org`), оба берут полный хост.
IP-адреса и односегментные хосты (`localhost`) используются целиком.

**Кастомные алиасы** заводит команда `alias`:

```bash
mono-vcs alias ls                       # все алиасы всех видов
mono-vcs alias ls remote                # только remote
mono-vcs alias remote work gitlab.mycompany       # синоним системного алиаса
mono-vcs alias remote api https://gitlab.mycompany.com/grp/api.git  # конкретный репо
mono-vcs alias remote -d work           # удалить
```

Вторым аргументом можно передать полный URL, хост, системный или уже
существующий кастомный алиас — сохраняется всегда **полное нормализованное
значение** (`gitlab.mycompany.com` или `gitlab.mycompany.com/grp/api`), а не сам
алиас. Имя алиаса не должно совпадать с системным и не может содержать пробелов,
запятых, `/` и `:`.

Файл — `~/.local/mono-vcs/aliases.json` (меняется ключом `aliases-path` в
конфиге):

```json
{
  "remotes": {
    "work": "gitlab.mycompany.com"
  }
}
```

Формат рассчитан на другие виды алиасов в будущем — `alias` принимает вид первым
аргументом (`alias remote ...`), и сейчас поддержан только `remote`.

## Тесты

```bash
make test         # go test ./...
make test-race    # с детектором гонок
make test-v       # подробно
```

Тесты не ходят в сеть: GitLab REST мокается через `httptest`, git-операции
выполняются над настоящими временными репозиториями.

## Структура

```
internal/
├── app/        общие типы (Args, Context)
├── colors/     ANSI-цвета
├── config/     чтение/запись конфига (JSON), применение дефолтов
├── output/     печать ошибок, таблица features
├── prompts/    интерактивные промпты (токен, ввод значений)
├── repos/      поиск локальных репо, --repo фильтр
├── remotes/    сбор git-remote'ов, нормализация URL, системные алиасы
├── aliases/    кастомные алиасы (JSON, ~/.local/mono-vcs/aliases.json)
├── selector/   общий отбор репозиториев по -repo/-feat/-remote
├── gitlab/     REST-клиент GitLab
├── gitops/     обёртки над git + per-repo воркеры
├── jobs/       параллельный per-repo раннер
├── dryrun/     печать dry-run планов
├── cli/        парсинг флагов + диспетчер + политика токена
└── commands/   оркестрация каждой подкоманды
```
